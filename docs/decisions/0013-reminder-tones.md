# 0013 — A reminder rings for ten seconds, via the file

**Status:** Accepted. Extends [0012](0012-task-reminders.md).

**Decision:** A task reminder plays a bundled ~10-second tone and stops. The
duration lives in the audio file, each tone owns its own Android notification
channel, and the default is `ReminderTone.chime`. **Alarms are untouched.**

## Context

The ask was for a reminder that "works like a ringtone — ten seconds and then
stop", with the sound changeable by the user and a default chosen for them.

Three platform facts shaped everything:

1. **Nothing in Dart can stop a notification's sound.** The OS plays the
   channel's sound once, to the end of the file. There is no duration
   parameter, no stop call, no callback. So the duration *is* the file length —
   ten seconds of sound means a ten-second file.
2. **A notification channel is immutable once created.** The user owns its
   settings; `createNotificationChannel` on an existing id updates only the
   name and description. A channel's **sound cannot be changed**, which means
   "let the user pick a different sound" cannot be done by editing one channel.
3. The alternatives that *could* control duration in code — a looping
   `FLAG_INSISTENT` notification cancelled by a timer, or a foreground service
   playing audio — all require app code to be running at the moment the
   reminder fires. On Android that is exactly what cannot be relied on, which
   is the whole reason [0010](0010-android-first-os-level-alarms.md) exists.

## Value and risk, per option

| Option | Value | Risk | Verdict |
|---|---|---|---|
| **A. A 10-second file as the channel sound** | Works with the app killed, which is the only case that matters. No new permissions, no service, no background isolate. | ~313 KB per tone in the APK. Duration is fixed at build time. | **Chosen** |
| B. Looping notification + a timer that cancels it | Duration controllable at runtime. | Needs the process alive when the reminder fires — the assumption 0010 was written to escape. Fails silently when Android has killed the app, i.e. normally. | Rejected |
| C. Foreground service playing audio | Full control, including fade and stop. | `FOREGROUND_SERVICE` plus a typed permission, a service declaration, a persistent notification of its own, and Play policy scrutiny — for a ten-second chime. | Rejected |
| D. In-app audio layered on the notification | Exact timing while the app is open. | The app is usually *not* open when a reminder fires, so it solves the easy case; and when it is open the user would hear the sound twice. | Rejected |

### Letting the user change it, given fact 2

| Option | Verdict |
|---|---|
| **One channel per tone, created on selection, others deleted** | **Chosen.** The only approach that actually changes the sound. Bounded because the tone set is a closed enum. |
| One channel, swap the sound | Impossible — see fact 2. |
| Send the user to Android's channel settings to pick any system sound | Rejected for now: it needs an intent the plugin does not expose, and it cannot offer a ten-second sound, which is the point of the feature. Still the honest escape hatch if an arbitrary file is ever wanted. |

## Consequences

- Three bundled tones at 10.0 s, 16 kHz mono, ~313 KB each (~940 KB of APK).
  16 kHz because nothing in a chime exceeds 2 kHz, and 44.1 kHz stereo would
  have cost nearly three times as much for no audible gain.
- **The tones are placeholders**, generated by
  `tool/generate_reminder_tones.py` (no third-party dependencies). They are
  committed so the feature is complete and testable end to end. Replacing one
  is a file swap plus a bump of `reminderChannelVersion` — *not* a code change.
- `reminderChannelVersion` exists because of fact 2: replacing a tone's audio
  without changing the channel id would leave every existing install playing
  the old sound forever. Bumping it resets the user's own per-channel tweaks,
  so it is bumped only when audio actually changes.
- Switching tone deletes the channels for the others. Without that, every tone
  the user ever tried would stay listed under "Task reminders" in Android
  settings with its own volume and vibration switches.
- **`AudioAttributesUsage.notification`, not `alarm`.** Alarm usage plays
  through the alarm stream and pierces silent mode and Do Not Disturb. That is
  right for an alarm clock and wrong for a nudge about a calendar block — a
  reminder that overrides DND in a meeting is what gets an app muted
  permanently. One line to flip if reminders should be unmissable.
- "Device default" is offered and is **honestly labelled as brief**, because it
  is the user's own notification sound and gives no ten-second behaviour. It is
  also the fallback that keeps working if a bundled file is ever removed.
- iOS keeps the system sound: a custom iOS notification sound must be bundled
  in the Xcode project, which this change does not touch. Android is the
  primary platform (0010).
- The tone is a parameter to `ScheduledNotifier.sync` rather than notifier
  state, because the channel must exist before the first notification is
  scheduled against it.
- The initial preference read is async and fired from the constructor, so a
  user who picks a tone before it lands would have had their choice
  overwritten. Whoever settles the question first wins, and there is a test for
  it.
- **Alarms are unchanged** — same channel, same sound, same ring-until-dismissed
  behaviour. This was an explicit requirement.
- **Unverified:** whether a ten-second notification sound plays to completion on
  a real device, and whether any OEM truncates it. Needs the device pass.
